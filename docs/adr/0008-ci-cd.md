# ADR-0008: CI/CD com GitHub Actions

- **Status:** Aceito
- **Data:** 2026-11-08

## Contexto

O ADR-0002 escolheu o GitHub Actions para CI/CD e o Renovate para manter as dependências. O ADR-0007 definiu regras de qualidade (testes, cobertura, Sonar, acessibilidade) que só bloqueiam PRs quando houver pipelines. O app é distribuído como app-image do Windows (ADR-0002), e o fluxo de trabalho usa squash merge com o título do PR como mensagem do commit (`CONTRIBUTING.md`).

O detalhamento e o passo a passo de configuração estão em [`docs/ci-cd.md`](../ci-cd.md).

## Decisão

1. **Três workflows:**
   - `pr-checks.yml`: título do PR e revisão de dependências.
   - `ci.yml`: back, front, E2E e Sonar.
   - `release.yml`: release-please e pacote para Windows.
2. **Ordem de entrada:** o `pr-checks.yml` e o `renovate.json` entram agora. O `ci.yml` e o `release.yml` entram com o esqueleto do projeto, porque dependem do `pom.xml` e do `package.json`.
3. **CI:**
   - Jobs `backend`, `frontend`, `e2e` e `sonar`, com filtro por pasta.
   - Versões de Java e Node lidas de `.java-version` e `.nvmrc`.
   - Cache de Maven e npm.
   - Meta de menos de 10 minutos por PR.
4. **Título do PR validado** com `amannn/action-semantic-pull-request`:
   - Tipos e escopos do `CONTRIBUTING.md`.
   - Descrição em minúscula, sem ponto final e com até 72 caracteres.
5. **Revisão de dependências** com `actions/dependency-review-action`, falhando em vulnerabilidade alta ou crítica.
6. **release-please:**
   - PR de release com SemVer (minor em breaking change antes da 1.0).
   - `CHANGELOG.md` em português e versão sincronizada no `pom.xml` e no `package.json`.
   - Título `chore: release X.Y.Z`.
   - Token fine-grained próprio (`RELEASE_PLEASE_TOKEN`), para que o PR de release dispare os checks.
7. **Pacote para Windows** num runner Windows: `jlink` + `jpackage --type app-image`, compactado em zip com checksum SHA-256 e anexado ao GitHub Release. Sem assinatura digital.
8. **Renovate:**
   - Agenda semanal e grupos (Angular, Spring Boot, testes, Actions).
   - Versões exatas no npm.
   - Espera mínima de 3 dias após cada publicação.
   - Automerge de patch e minor em dependências de desenvolvimento e Actions, com CI verde.
   - Versão do Node sincronizada no `pom.xml`.
9. **Dependabot só com alertas,** sem PRs.
10. **Segurança dos pipelines:**
    - Permissões mínimas por job e Actions fixadas pelo SHA do commit.
    - Sem `pull_request_target` e com checkout sem credenciais persistidas.
    - `concurrency` e timeout em todo job.
11. **Recursos de segurança do GitHub:** secret scanning com push protection e CodeQL no modo padrão.
12. **Checks obrigatórios** adicionados à proteção da `main` depois da primeira execução de cada um.

## Consequências

**Positivas**
- Toda mudança na `main` passa pelos mesmos checks, e o histórico segue o Conventional Commits mesmo com squash merge.
- Versão, changelog e pacote do Windows saem do mesmo fluxo, sem passos manuais além de aceitar o PR de release.
- Dependências ficam atualizadas com pouco esforço, e as atualizações arriscadas continuam passando por revisão.
- A cadeia de fornecimento dos pipelines fica protegida por SHAs fixos e permissões mínimas.

**Negativas / riscos**
- O token do release-please expira e precisa ser renovado; um token vencido faz o PR de release parar de aparecer.
- O runner Windows é mais lento que o Ubuntu, mas só roda em releases.
- Sem assinatura digital, o Windows mostra o aviso do SmartScreen na primeira execução.
- A descrição dos PRs do Renovate fica em inglês, uma exceção à regra de idioma.

## Alternativas consideradas

- **Dependabot para atualizações:** descartado; não agrupa bem as dependências que precisam andar juntas, como Angular e TypeScript.
- **semantic-release:** descartado; publica a cada merge, sem um PR de release para revisar a versão e o changelog.
- **GitHub App próprio em vez de token fine-grained:** descartado por ora; mais seguro, porém mais trabalhoso para um projeto de uma pessoa só.
- **`pull_request_target` para o check de título:** descartado; dá acesso a secrets em PRs de terceiros, e o repositório não recebe PRs de forks.
- **Instalador MSI (`jpackage --type msi`):** descartado; exige o WiX Toolset, e quem instala e inicia o app é o My Collection.
- **CodeQL por workflow próprio (modo avançado):** descartado; o modo padrão cobre Java e TypeScript sem YAML.
- **Cache dos navegadores do Playwright:** descartado; a documentação do Playwright recomenda instalar a cada execução.
